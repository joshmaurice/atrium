# Atrium — User Accounts & Persistence Design Brief

## Overview

Currently Atrium is a stateless experience: a user connects with a random
`sessionId`, explores a shared world, and when they close the tab — everything
is gone. There is no way to return as "the same person," no way to save state,
and no personal space.

This brief captures the design for adding user identity and per-user persistence
to Atrium. It covers auth, the persistence model, the home area concept, and
the changes needed to each layer of the stack.

## Related Design Briefs

- `DESIGN-user-objects.md` — The `ATRIUM_user_object` extension schema. That
  brief defines *what a user object is* as a glTF concept. This brief defines
  *how users, their accounts, and their saved data* exist in the system.
  The `ATRIUM_user_object` implementation remains deferred per the decision
  in that document; extras are sufficient for this phase.

## Principles

1. **Browse without an account.** The "browser model" from Atrium's design
   philosophy applies here. Any user can load a world and explore without
   registering. Accounts are required only to *save*, *own*, or *configure*.

2. **Lowest viable ceremony.** No email verification, no password complexity
   rules, no onboarding flow. Username + password is enough. A user can
   register in under 30 seconds and be in their home world.

3. **glTF is the save format.** A user's saved world is a self-contained glTF
   document with buffers embedded as base64 data URIs — matching what
   `world.serialize()` already produces. GLB and externally-stored resources
   are future options, not Phase 1.

4. **Extras before extensions.** Per-node user metadata (ownership, display
   name, creation date) lives in `extras.atrium` — simple, free-form, no
   loader ceremony. Formal glTF extensions (`ATRIUM_user_object`,
   `ATRIUM_interactivity`) are for *behaviour-changing* node types and are
   deferred until needed.

5. **Server-authoritative saves.** "Save this world" means the *server*
   serializes its own authoritative SOM (the machinery already exists in
   `world.serialize()`) and persists the result. The design must not accept a
   client-uploaded world document as a normal save; that would create a second
   authority path. Client-supplied glTF upload is a separate, later "import"
   operation with its own validation story.

6. **The database is the authority on permissions.** `extras.atrium.owner` in
   the serialized glTF is exported *provenance metadata only* — it never grants
   permissions, because any client can edit JSON. The server decides
   authorization from authenticated state, then serializes ownership into the
   glTF as portable information.

## Identity Model

Five distinct identities, each with different lifetimes and properties:

| Identity | Nature |
|---|---|
| `userId` | Stable UUID, server-generated on registration. Lives in the database permanently. |
| `sessionId` | New UUID per WebSocket connection. Existing behaviour — generated by the client on page load. |
| `avatarNodeName` | **Server-assigned** at WebSocket session establishment. Returned in the `hello.server` response. Uniqueness guaranteed by construction (e.g. `avatar-<8 hex>` with retry-on-collision, or full UUID). No client-side derivation convention. |
| `authSessionId` | Opaque cookie value, server-generated on login. Lives in the `auth_sessions` table with expiry. Distinct from the WebSocket `sessionId` — reserved for auth only. |
| `displayName` | Mutable, cosmetic. User-chosen for accounts. `User-xxxx` / `Guest-xxxx` for anonymous sessions. Continues to live in `join.avatar.displayName` and `node.extras.displayName`. |

### Key constraint being broken

Currently `_onView()` and `_onJoin()` in `AtriumClient.js` resolve peer avatar
nodes by *recomputing* the node name from the session ID:
`'User-' + msg.id.slice(0, 4)`. Peer routing structurally depends on
`sessionId → displayName → node name` being derivable. The `slice(0,4)`
convention also limits the namespace to ~65K names (~7% collision probability
at 100 concurrent users).

Phase 1 replaces this name-reconstruction convention with a server-assigned,
server-enforced `avatarNodeName` and an explicit mapping established at
presence time.

## Architecture

```
Client (apps/client)
  │
  ├── HTTP (same origin) ──► /api/auth/register    (POST)
  │                            /api/auth/login       (POST)
  │                            /api/auth/logout      (POST)
  │                            /api/auth/me          (GET)
  │                            /api/worlds           (GET, POST)
  │                            /api/worlds/:id       (GET, PUT, DELETE)
  │
  └── WebSocket (SOP) ──► Same origin, cookie sent on upgrade
                            No auth tokens in SOP messages.
                            SOP remains a live-session protocol only.
  │
  Atrium Server (packages/server)
  │   │
  │   ├── lib/auth.js        — register, login, logout, cookie mgmt
  │   ├── lib/db.js          — SQLite/Postgres connection + migrations
  │   ├── lib/world-store.js — CRUD for user worlds over HTTP
  │   └── lib/session.js     — resolve cookie → userId at WS upgrade
  │
  SQLite (Phase 1); Postgres adapter may be added later
      ├── users        (id, username, password_hash, display_name, created_at)
      ├── auth_sessions (id, user_id, created_at, expires_at)
      ├── worlds       (id, owner_user_id, slug, name, document,
      │                  visibility, created_at, updated_at)
      └── preferences  (user_id, key, value)
```

The `worlds` table uses `visibility` + `slug` to leave the path open for
`/public/<user>/<slug>` style addressing later.

## Auth Flow

### Phase 1 assumption

The bundled web client and the world server share an origin. Cookie-based
sessions depend on this. Cross-origin / independently-hosted-client /
federated auth is out of scope for Phase 1 — it would require bearer
credentials or an OAuth-like scheme (a recorded future problem, not an
accident).

Achieved operationally by one of:
- The new Atrium HTTP server also serves `apps/client` as static files, or
- A same-origin reverse proxy serves the client and proxies `/api/*` plus the
  WebSocket endpoint to the Atrium server.

The browser must see the client, account API, and WebSocket endpoint as the
same origin.

### Session cookie attributes

```
atrium_auth_session=<id>; HttpOnly; Secure; SameSite=Lax; Path=/
```

A `__Host-` cookie name may be used if convenient (e.g.
`__Host-atrium_auth_session`) provided the deployment satisfies the
corresponding requirements (no `Domain` attribute, `Path=/`, `Secure`).

### Registration
1. Client sends `POST /api/auth/register` with `{ username, password }`
2. Server hashes password (Argon2id), creates user row
3. Server creates auth session row, sets `atrium_auth_session=<id>; HttpOnly; Secure; SameSite=Lax` cookie
4. Client receives cookie automatically; no token handling needed

### Login
1. Client sends `POST /api/auth/login` with `{ username, password }`
2. Server verifies hash, creates session row, sets cookie
3. Same as registration step 3-4

### Logout
1. Client sends `POST /api/auth/logout` (cookie sent automatically)
2. Server deletes session row, clears cookie

### Session continuity
- On successful login: server generates `authSessionId` (cryptographically random),
  stores it in the `auth_sessions` table, and sets
  `atrium_auth_session=<id>; HttpOnly; Secure; SameSite=Lax`
- On page load / WebSocket upgrade, the server reads the cookie, resolves
  `authSessionId → userId` (or null for anonymous), and attaches `userId` to the
  server-side session object. No token appears in any SOP message.
- The `hello` schema does not change for auth purposes.
- Session expiry column + periodic sweep of the `auth_sessions` table.

### Anonymous sessions
- No cookie → server treats connection as anonymous (userId = null)
- Anonymous users see public worlds, cannot save
- Visible in-world as `Guest-xxxx` (matching current behaviour)

### Security baseline

- Password hashing: **Argon2id** (or scrypt)
- Minimum password length: **15 characters**; no composition/complexity rules
- Check newly chosen passwords against a blocklist of common, expected, or
  known-compromised passwords
- Username normalization + uniqueness enforcement
- **Rate limiting** on register/login — per-IP throttle
- **Honeypot field** on the registration form (bot resistance from day one)
- Generic login-failure messages ("Invalid credentials" — don't reveal which
  field was wrong)
- **Validate the `Origin` header on WebSocket upgrade** — cookie auth otherwise
  lets any website open an authenticated socket from a visitor's browser
- **CSRF protection** — validate `Origin` on state-changing HTTP routes, keep
  CORS closed to foreign origins, retain `SameSite=Lax`. Optionally require an
  Atrium-specific request header (cross-origin pages cannot set custom headers
  without a CORS preflight that will never be approved). No token-synchronizer
  machinery needed for Phase 1.
- HTTPS/WSS in deployment
- Session expiry column + periodic sweep of the `auth_sessions` table.
- Database backups — the server now holds credentials/PII for strangers on a
  public endpoint. (JWT signing-key management is no longer needed.)

## Peer Identity & Routing

Replace the current name-reconstruction convention with the following design.
Verified facts it builds on: `add.json` already defines an optional `id`
("Session UUID — identifies the sender when adding an avatar node"); the
server already uses `msg.id` as the avatar marker (`session.js:204`) but
strips it from the rebroadcast; `join.json` already has an `avatar` object
(`displayName`, `avatarURL`, position, rotation); and the server already
sends the newcomer one bootstrap `join` per existing peer at hello time
(`session.js:146-155`).

### a. Server-assigned avatar node names

The server assigns `avatarNodeName` when the WebSocket session is established
and returns it in the `hello.server` response (schema change: `hello.server`).
The client adopts the assigned name for its avatar descriptor. Naming scheme
is up to implementation (e.g. `avatar-<8 hex>` with retry-on-collision, or
full UUID) — the requirement is server-guaranteed uniqueness; length is
aesthetic once uniqueness is enforced by construction.

### b. Assignment is enforced, not advisory

The server rejects an avatar `add` whose `node.name` does not match the
assigned name (consistent with "invalid messages never touch world state").
Otherwise clients can still claim arbitrary names and the assignment
accomplishes nothing.

### c. Stamp `id` on rebroadcast — server's own value

The outbound avatar `add` broadcast carries `id: session.id`, stamped by the
server. Never echo the client-supplied `msg.id` — the server does not
currently verify it matches the session, and echoing it would allow sender
impersonation. (`add.json` already permits `id`, so this leg may need no
schema change — but it needs tests either way.)

### d. Additional integrity rules

- If an avatar `add` contains `msg.id`, require it to equal the actual
  server-side `session.id`.
- Reject use of the session's assigned avatar node name in an `add` that is
  not the session's valid avatar add.
- At `hello`, reject a duplicate **currently live** `sessionId` rather than
  allowing two WebSocket connections to share one.

### e. Enrich `join` with `avatar.nodeName`

Schema change to `join.json` (the `avatar` container already exists). Include
it in the bootstrap joins sent to a newcomer (server knows every established
peer's node name at that point) and in the newcomer-announcement join (server
now knows the name at hello time, before the avatar `add` even arrives).

### f. Client peer map

Evolve `_peerSessions` into peer metadata: `sessionId → { nodeName, displayName }`,
populated from `join` and `add`. Routing uses `nodeName` exclusively; UI uses
`displayName`. A `view` for an unknown session is dropped silently. A `view`
for a known session whose node is not yet in the SOM (mapping arrived before
the `add`) is also skipped without error.

### g. Display name transport

Cosmetic names travel in `join.avatar.displayName` (existing field) and
`node.extras.displayName`. No routing path may depend on deriving names from
session IDs.

**Phase-1 initialization rule:** `displayName = username` at registration.
The server is authoritative for the display name distributed to peers:
`join.avatar.displayName` comes from server-known user/session state, and the
server canonicalizes or overwrites avatar `node.extras.displayName` rather
than trusting an arbitrary client-supplied value. Editable/custom display
names can be deferred.

**Anonymous naming:** Anonymous users appear as `User-xxxx` (matching current
Atrium behaviour). Intentionally changing to `Guest-xxxx` is a Phase-1 UX
change that must be called out explicitly if desired.

### Schema-change inventory

| Change | Type |
|---|---|
| `hello.server` — add assigned `avatarNodeName` | Schema + server + client + tests |
| `join` — add `avatar.nodeName` | Schema + server + client + tests |
| Avatar `add` — reject `msg.id` ≠ server `session.id` | Server behavior + tests |
| Avatar `add` — reject name ≠ assigned name | Server behavior + tests |
| Avatar `add` rebroadcast — stamp server-side `id` | Server behavior + client + tests (schema already permits `id`) |
| `hello` — reject duplicate live `sessionId` | Server behavior + tests |

Per AGENTS.md rule 1, schemas, validators, and tests update atomically.

## Persistence Model

### Phase-1 semantics: what "save" means

A Phase-1 saved world is a **personal, avatar-free snapshot of the currently
hosted live world**, loaded later as a static client-side world. (Loading a
persisted world back into a live multiplayer server runtime is Phase 2 work.)

### What gets saved

A saved world is a **self-contained glTF document** with buffers embedded as
base64 data URIs — matching what `world.serialize()` already produces.

**Avatar exclusion.** `world.serialize()` currently filters only
externally-ingested reference nodes; avatars are included. Add a
persistence-serialization option (e.g. `serialize({ excludeNodes })`) fed
from the server's own tracked `session.avatarNodeName` values — not from any
extras marker, matching the design's authority philosophy. `som-dump`
serialization continues to include avatars; persistence excludes them. These
are two modes of one serializer, not a behavior change to `som-dump`.
GLB and externally-stored resources are future options.

Extras carry user-level data per node as *provenance metadata only*:

```json
{
  "extras": {
    "atrium": {
      "owner": "user-uuid-here",
      "displayName": "Josh's Tree",
      "createdAt": "2026-08-15T00:00:00Z",
      "tags": ["favorite", "decorative"]
    }
  }
}
```

The database is the authoritative source for ownership. These extras are
portable information only — the server writes them during serialization based
on its own auth state, not on trust of what the client sent.

### World CRUD (HTTP — not SOP)

World operations live over HTTP, not SOP. Rationale:

- A world is a glTF resource loadable by URL. `GET /api/worlds/:id` returning
  glTF means a saved *public* world is an ordinary glTF URL, loadable by the
  existing static path — persistence extends the browser model instead of
  creating a second proprietary loading mechanism. (Private worlds require
  auth, so "any viewer" applies to public worlds only.)
- Multi-megabyte world documents do not belong on an ordered WebSocket that
  carries 20 Hz view traffic.

```
GET    /api/worlds          (list own worlds — returns { id, slug, name, visibility, updated_at })
POST   /api/worlds          (create — body: { slug, name }; server sets visibility = "private")
GET    /api/worlds/:id      (fetch — returns the full glTF document)
PUT    /api/worlds/:id      (update metadata or trigger save)
DELETE /api/worlds/:id
```

### Server refactor

`createSessionServer()` currently constructs its own bare
`WebSocketServer({ port })`. Restructure to an HTTP server that serves `/api/*`
and handles the WebSocket upgrade on the same port.

### Save flow (server-authoritative)
1. Client sends `PUT /api/worlds/:id` (or triggers auto-save)
2. Server validates cookie → resolves userId → verifies world ownership
3. Server serializes its authoritative SOM via `world.serialize()`
4. Server persists the result as base64-embedded glTF JSON in the `document` column
5. Server responds `{ id, slug, name, updated_at }`

### Load flow
1. Client sends `GET /api/worlds/:id` (cookie sent automatically)
2. Server validates cookie → resolves userId; only the owner may load a Phase-1 world
3. Server returns the full glTF document
4. Client loads the scene into its SOM/DocumentView

## Home Area

Deferred to Phase 2 (see Phasing below).

On login, a user would automatically load their home world — their personal
space. If they haven't set one, the server creates a default empty world
(a skybox, a ground plane, and their avatar).

The home world is:
- Saved automatically on mutations (debounced) AND on disconnect (final flush)
- Loaded automatically on login
- Able to contain teleporters/gates to public worlds
- A place to store collected objects, notes, and interface configuration

(Phase 1: home world is not auto-loaded. The user's saved worlds appear in a
list; they pick one to load.)

## Interface Configuration

User preferences (default FOV, control scheme, theme) are stored in the
`preferences` table — client settings, not world data. Saved per user, loaded
on login, applied when the client connects. These are not yet in scope for
Phase 1.

## Phasing

### Phase 1 — Identity & Core Persistence

- Identity model: `userId`, `sessionId`, server-assigned `avatarNodeName`, `authSessionId`, `displayName`
- Server-assigned and server-enforced avatar node names (reject `add` with wrong name)
- Stamp `session.id` on avatar `add` rebroadcast (never echo client `msg.id`)
- Enrich `join` with `avatar.nodeName` for explicit peer routing
- Evolve `_peerSessions` into `sessionId → { nodeName, displayName }` map
- Register / login / logout with HttpOnly cookie sessions
- `authSessionId → userId` binding at WebSocket upgrade time
- Server restructure to HTTP + WS on same port
- World CRUD over HTTP (list / create / fetch / update / delete) — all private
- Server-authoritative saves via `world.serialize({ excludeNodes })` excluding avatars
- Persisted format: self-contained glTF JSON with base64 data URIs
- Phase-1 saved world: avatar-free snapshot of the live world, loaded as static client-side scene
- Security baseline: Argon2id, rate limiting, Origin validation on WS + HTTP, SameSite+Lax, custom header CSRF, honeypot, session sweep
- No home world, no auto-save, no preferences UI

### Phase 2 — Home World & Auto-Save

- Default home world creation on first login (empty skybox + ground plane + avatar)
- **Server-side world loading** — load a persisted world back into the live multiplayer server runtime (the critical prerequisite for multiplayer home worlds)
- Auto-load home world on login
- Server-side debounced auto-save after SOM mutations
- Disconnect-save as final flush (not the only save — periodic saves handle crashes)
- World visibility (public / private toggle)
- `/public/<user>/<slug>` URL path for public world sharing

### Phase 3 — Power User Features

- Remembered-guest identity (anonymous sessions that persist across browser close/reopen) with migration path to accounts
- User-object ownership and provenance UI (leaning on `extras.atrium.owner` as display metadata, with the database as authoritative source)
- Preferences system (FOV, controls, theme) stored in `preferences` table
- Client import of user-uploaded glTF files (separate from server-authoritative saves; own validation story)
- `ATRIUM_user_object` extension implementation remains deferred — its open questions (subtree instancing, script sandboxing, property vocabulary) should not be solved simultaneously with auth and persistence

## Implementation Sequencing

When implementation begins, **land the peer-identity/routing refactor first and
alone**, under the existing anonymous flow. It is the only piece that touches
the live protocol, it is fully testable without any auth or persistence code
existing, and proving it out first de-risks everything downstream. Auth +
persistence follow as a second step.

### Order of operations

1. **Peer identity & routing** (Phase 1, step 1 — anonymous, testable standalone)
   - Server assigns `avatarNodeName`, returns in `hello.server`
   - Server enforces: `add` with wrong name rejected, `msg.id` must match `session.id`
   - Server stamps its own `session.id` on avatar `add` rebroadcast
   - Server rejects duplicate live `sessionId` at hello
   - Enrich `join` with `avatar.nodeName`
   - Evolve `_peerSessions` into `sessionId → { nodeName, displayName }` peer metadata
   - Server-authoritative display name in `join` and `node.extras`
   - Update schemas, validators, and tests atomically (per AGENTS.md rule 1)
   - No auth, no persistence — works entirely under current anonymous flow

2. **Auth + persistence** (Phase 1, step 2)
   - HTTP server restructure
   - Auth endpoints (register/login/logout with HttpOnly cookies)
   - Database schema + migrations
   - World CRUD over HTTP with server-authoritative saves
   - Security baseline
